# 요약 미생성 사고 — 원인, 수리, 관측성 보완 (2026-08-06 ~ 08-07)

증상 신고: **배포(`https://lbnote.litbig.com:49152`)에서 회의록에 전사만 남고 요약·액션이 비어 있다.**
전사는 정상, 화면에는 "자동 요약이 비어 있습니다" 회색 문구만.

결론부터: 원인은 음원도, 프롬프트도, 자격증명 만료도 아니었다. **병렬 워커가 사용자 자격증명을
잃고 있었다.** 요약·추출은 항상 태스크가 2개 이상이라, 배포에서 요약은 **100% 실패**했고
잡은 `status=done` 으로 끝나 실패를 아무도 몰랐다. dev 는 전역 claude 로그인이 있어 증상이
재현되지 않았다.

이 문서는 진단 사슬(전부 증거 기반), 근본 원인, 왜 테스트·dev 가 못 잡았는지, 그리고 같은 사고가
다시 조용히 지나가지 않게 하려고 넣은 관측성 보완을 기록한다.

## 1. 최초 오판 정정

첫 응답에서 "배포 인스턴스에 도달할 수 없다"고 보고했다. **틀렸다.**
`curl -k https://lbnote.litbig.com:49152/` → **200**. 컨테이너에서 배포본에 정상 도달한다.

이후 진단은 admin API 를 주 채널로 삼았다. 이 컨테이너에는 docker 소켓·호스트 마운트·배포 서버
SSH 키가 없어 **API 가 배포본을 볼 수 있는 유일한 창**이다.

## 3. 근본 원인 — ContextVar 는 스레드를 넘지 않는다

`src/postprocess/orchestrator.py` 의 `_run_parallel` 이 `ThreadPoolExecutor` **워커 안에서**
`contextvars.copy_context()` 를 불렀다. 워커 스레드의 컨텍스트는 **비어 있다** — 스레드는
컨텍스트를 상속하지 않는다. 그래서 빈 컨텍스트를 복사했고, 사용자 자격증명은 조용히 사라져
전역 폴백으로 떨어졌다. 배포 컨테이너에는 전역 claude 로그인이 없으므로 실패했다.

같은 경로로 **취소 이벤트와 실패 카운터도 함께 유실**됐다. 그래서 감사 로그에는
`failures=none` 이 남았다 — 실패를 세는 카운터가 실패와 같이 죽었다.

### 올바른 패턴

`Context.run` 은 쓸 수 없다. 같은 Context 를 동시에 `run` 하면
`cannot enter context: already entered` 가 난다. **제출 스레드에서 값을 스냅샷**하고 워커에서
다시 심어야 한다.

```python
# 제출 스레드의 ContextVar 값 스냅샷(자격증명·취소 이벤트·실패카운터 등 전부).
snapshot = list(contextvars.copy_context().items())

def _call(thunk):
    # 워커 스레드에 값을 심고, 끝나면 원복한다(풀 스레드가 재사용되므로 누수 금지).
    tokens = [(var, var.set(val)) for var, val in snapshot]
    try:
        ...
    finally:
        for var, token in reversed(tokens):
            var.reset(token)
```

수리 커밋: `7f3bba5` (PR #65).

## 4. 왜 못 잡았나

두 가지가 겹쳐서 이 버그가 배포까지 갔다.

**테스트**: 기존 단위 테스트는 core 를 **직접** 불렀다. 잡 스레드에서 워커 스레드로 넘어가는
경계를 건너뛴다. 그 경계가 정확히 버그가 있던 곳이다.

**dev 환경**: dev 는 `HOME=/home/evan` 이고 전역 `~/.claude` 로그인이 있어 **폴백이 성공한다.**
배포 컨테이너는 `claude_auth: {"ok": false, "reason": "no_credentials"}` 다. 즉 로컬에서는
증상이 나올 수 없었다.

배포 조건을 로컬에서 재현하려면 `HOME` 을 바꾸는 것만으로는 부족하다. `_resolved_home()` 이
sudo 실행을 `SUDO_USER` 의 홈으로 되돌리므로 **`SUDO_USER` 도 지워야** 한다. 이 조건에서 A/B 를
돌려 원인을 확정했다.

| | 수리 전 | 수리 후 |
|---|---|---|
| `callsOk` | `{summarize: 0, extract: 0}` | `{summarize: 1, extract: 1}` |
| `summary.backend` | `''` | `'agent_cli'` |
| 산출 | 안건 0 | 안건 4 / 액션 1 |

수리 전 값이 배포에서 관측된 것과 정확히 일치한다.

## 5. 관측성 보완

원인을 고쳤어도 "조용히 done" 구조가 남으면 다음 사고도 같은 방식으로 지나간다. 세 가지를 넣었다.

### 5.1 병렬 경로 회귀 테스트 (PR #65, `tests/test_core_parallel_context.py`)

n=1 은 이 버그를 못 잡는다(단일 태스크는 제출 스레드에서 실행). **n>=2 에서만** 잡힌다.
그래서 n=1,2,4,8 을 모두 검사하고, 풀 스레드가 호출 간에 값을 남기지 않는지도 본다.

### 5.2 업로드 경로 종단 검증 (PR #66, `tests/test_upload_job_credential.py`)

**HTTP 업로드부터** 돌려서, LLM 백엔드가 호출된 순간에 사용자 자격증명이 보였는지를 백엔드가
직접 기록해 검사한다. 전역 폴백으로 떨어지면 `None` 이 기록된다. secret 은 남기지 않고
`type` 만 본다.

### 5.3 진행 표시 (PR #66 + web #49)

긴 회의는 `phase` 가 `summarizing` 에 고정된 채 십수 분이 흐른다. 아무 정보가 없으면 사용자가
멈춘 줄 알고 새로고침해 **같은 회의를 두 번 돌린다.**

- `src/progress.py` (신규) — `src/cancellation.py` 와 같은 ContextVar 채널. 단계·창 진행을 보고
- 서버가 문구를 만든다: `요약/추출 진행 중입니다. 구간 3/8 완료.` (게이트 `label`·`reasonHint` 와 같은 규약)
- 프론트 폴링 마감을 **진행 기반**으로 전환. `status|phase|progress` 서명이 바뀌면 유휴 타이머 리셋.
  유휴 30분 / 총 3시간. 종전 고정 마감은 오래 걸리는 회의를 살아있는데도 끊었다

진행 보고는 `_run_parallel` 의 스냅샷을 타고 워커까지 간다. 초기 구현에서 `on_done` 을
ContextVar 원복 **뒤에** 불러 워커에서 리포터가 사라졌고, 이걸 새로 쓴 테스트가 잡았다.

### 5.4 재요약 경로 진단 누락 (PR #67)

`_job_diag` 를 싣는 곳이 **업로드 경로 한 곳뿐**이어서, 재요약 잡의 `done` 응답에는 `diag` 가
없었다. `_empty_output_hint` 는 `diag` 를 읽으므로 **재요약 결과가 비어도 원인 문구가 나올 수
없었다.** 배포본 폴링에서 `diag: null` 로 확인했다.

재요약은 "요약이 비었다"를 되살리는 **복구 경로**다. 빈 요약으로 남은 회의를 재요약으로 살리다가
또 비면, 사용자는 지난 사고와 똑같이 이유를 알 수 없다.

## 8. 같은 버그가 다른 곳에 있는지

전수 확인했다. `copy_context()` 사용처는 `_run_parallel` 이 유일했다.

- `threading.Thread` 4곳(`ai_process`, `regenerate_meeting`, Drive 업로드, Drive 동기화)은
  자격증명을 **인자로 명시 전달**한다 — ContextVar 상속에 의존하지 않는다
- `asyncio.to_thread` 는 컨텍스트를 전파한다

버그 클래스는 봉쇄됐다.
