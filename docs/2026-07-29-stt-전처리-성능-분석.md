# STT 전처리(WPE) 성능 분석과 기본값 변경

작성일: 2026-07-29
서버: 171 (NVIDIA RTX PRO 6000 Blackwell)
상태: 기본값 변경 적용 완료 / GPU WPE 는 후속 개발 계획

---

## 1. 요약

"1시간 회의 처리에 왜 이렇게 오래 걸리나"에서 출발해, 처리 시간의 절반 이상이
**WPE 전처리**에 쓰이고 있음을 실측으로 확인했다. WPE 는 CPU 전용 구현이라 GPU 가 노는 동안
CPU 가 오디오 길이에 정비례하는 비용을 치르고 있었다.

기본값을 `ENHANCERS="wpe"` -> `""` 로 바꿨다. 다만 WPE 자체가 쓸모없는 것은 아니며,
**GPU 구현으로 옮기면 정확도를 그대로 두고 비용만 줄일 수 있다**는 것까지 확인했다(4절).

- 실효 RTFx 가 전 구간 **10.5 근처로 일정**했다. 문서상 RTFx 232 의 20분의 1이다.

- 55분 초과 구간은 `samples/asr test.m4a`(55분 실회의)를 루프해 채웠다.

부수 확인: `AGENT_CLI_TIMEOUT=600` 은 90분 회의에서도 여유가 있었다(요약 최대 185.8s,

## 3. 원인: WPE 가 STT 시간의 96%

`tools/bench_wpe_ablation.py`, 결과 `output/bench-wpe-ablation-20260729.json`. 30분 음원.

| 설정 | STT 소요 | 실효 RTFx |
| --- | --- | --- |
| `ENHANCERS=wpe` (당시 기본값) | 170.3s | 10.6 |
| `ENHANCERS=""` | **6.1s** | **295.1** |

28배 차이다. 두 실행 모두 모델 로드와 66/66 디코딩을 정상 수행했으므로 캐시 효과가 아니다.
**문서상 RTFx 232 는 전처리를 뺀 순수 추론 수치**였고, 운영 기본값에서는 10.5 로 떨어져 있었다.

### 왜 느린가

`src/backends/wpe_dereverb.py` 는 `nara_wpe.wpe.wpe`(numpy, **CPU 전용**, 단일채널)를 쓴다.

```
STFT size=512 shift=128  -> 16kHz 에서 주파수 빈 257개, 초당 프레임 125개
taps=25, delay=3, iterations=5
블록 300초 + 5초 crossfade overlap-add
```

주파수 빈마다 25차 선형예측을 5회 반복하며 공분산/역행렬을 계산한다. GPU 는 STT 에만 쓰이고
이 연산은 CPU 에서만 돌므로, GPU 가 6초에 끝내는 일에 CPU 가 164초를 더 붙인 셈이었다.

## 4. 정확도 대가: 음원 의존적

`tools/bench_wpe_wer.py`. reference 가 Clova STT 결과라 ground truth 가 아니므로
**절대값이 아니라 두 설정의 차이만** 의미가 있다.

| 음원 | 설정 | STT | WER | CER |
| --- | --- | --- | --- | --- |
| `ax과제회의` 83분 | wpe | 456.3s | 0.3934 | 0.2539 |
| (ref: `ax_tf_클로바.txt`) | 없음 | 15.4s | 0.3994 | 0.2598 |
| | **차이** | **30배** | **+0.006** | **+0.006** |
| `asr test.m4a` 55분 | wpe | 303.6s | 0.3631 | 0.2211 |
| (ref: `ax_vision_safety_클로바.txt`) | 없음 | 12.6s | 0.3904 | 0.2473 |
| | **차이** | **24배** | **+0.027** | **+0.026** |

- 두 번째 결과는 기존 `src/config.py` 주석에 있던 "asr test.m4a: WER 0.39->0.36,
  CER 0.25->0.22" 를 소수점까지 재현한다. 기존 근거는 정확했다.
- **WPE 효용은 음원에 따라 4.5배 갈린다**(0.6%p vs 2.7%p). 잔향이 있는 녹음일수록 값을 한다.

## 6. 후속 개발 계획: GPU WPE

### 6.1 검토했다가 접은 안 - auto 라우팅

"음질을 재서 필요할 때만 WPE" 가 자연스러워 보이지만, 현재 `decide_enhancers`
(`src/quality.py:108`)는 **네 갈래 전부 `["wpe"]` 로 시작**하고 GTCRN 추가 여부만 고른다.
WPE 를 끄는 판정은 존재한 적이 없다. 이 안을 하려면 잔향 측정기를 새로 만들어야 하는데,
단채널 잔향 추정(DRR/T60 blind estimation)은 그 자체가 연구 과제다.

### 6.2 채택 예정 - torch 구현으로 GPU 이전

`nara_wpe` 에는 PyTorch 구현 `nara_wpe.torch_wpe.wpe_v6` 가 함께 설치돼 있다.
60초 슬라이스로 동일 파라미터(taps=25, delay=3, iterations=5) probe 결과:

```
numpy / CPU   4.9초
torch / CUDA  0.9초        -> 5.6배
출력 상대오차 6.23e-13     -> 수치적으로 동일한 결과
VRAM peak     1642 MiB
```

오차 1e-13 은 근사가 아니라 **같은 계산**이라는 뜻이다. 정확도 회귀 위험이 없다.

전체 음원 환산(추정):

| 음원 | WPE 없음 | CPU WPE | GPU WPE |
| --- | --- | --- | --- |
| 30분 STT | 6s | 170s | 약 35s |
| 90분 STT | 17s | 480s | 약 85s |
| 90분 전체 | 5분25초 | 13분39초 | **약 6분33초** |

즉 90분 회의에서 **1분 8초를 더 쓰고 WER 최대 2.7%p 를 얻는** 거래가 된다.
현재의 "8분 14초를 더 쓰고 2.7%p" 와는 성립 여부가 다르다.

### 6.3 착수 시 확인할 것

1. **운영 블록 크기(300초)에서의 VRAM.** probe 는 60초에서 1642MiB 였다. 단순 환산하면
   300초에 약 8GB 인데, STT 백엔드가 상한 20GB 를 잡으므로 공존 가능성을 재야 한다.
   `complex64` 로 낮추면 절반이 되지만 반복 solve 의 수치 안정성을 확인해야 한다
   (numpy stft 는 complex128 을 반환한다).
2. **OOM 폴백.** GPU 실패 시 조용히 CPU 경로로 되돌아가야 한다(현재 구조상
   `_apply_wpe` 한 곳만 분기하면 된다).
3. **GPU 경합.** 전처리가 GPU 를 쓰기 시작하면 `_stt_semaphore` 범위 밖에서 VRAM 을
   잡게 된다. 슬롯 회계에 포함할지 결정이 필요하다.
4. **끝단 검증.** probe 는 슬라이스 단위였다. 실제 파이프라인에 넣어 `asr test.m4a` 로
   WER 0.3631 이 재현되는지 확인해야 한다.

### 6.4 그때 기본값을 어떻게 할지

GPU WPE 가 들어가면 `ENHANCERS` 기본값을 다시 `"wpe"` 로 되돌리는 것을 검토한다.
비용이 20% 수준으로 떨어지면 "느려도 정확한" 쪽이 기본값으로 맞다.
