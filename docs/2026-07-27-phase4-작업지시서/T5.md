## T5. 디스크 임계 워터마크 — 상시 판정 + 증가율/여유일수 산출 + 회수 레버

**목표**: `maintenance.disk_usage()` 가 조회만 하고 끝나는 현 상태에, WARN 80% / ERROR 90% 임계 판정과 `disk_high` 알림 발화, 그리고 증가율(GB/월)·남은 여유 일수 산출을 붙인다. 판정은 `WEB_CLEANUP_ENABLED` 게이트 **밖**(잡 GC 와 같은 상시 실행 구간)에 두어 정리 배치를 꺼도 디스크 알림이 함께 꺼지지 않게 한다. 아울러 T1 이 만든 `_health_snapshot()` 의 `reasons` 에 `disk_high` 를 편입해 "Slack 은 경고하는데 health 는 ok" 인 진실 둘 상태를 없앤다.

**우선순위 / 예상 공수**: P1 / 에이전트 7h (구현 4h + 테스트 2h + 런북 1h), [사용자 수행] 검증 1h

### 이 지시서가 지켜야 할 전역 배정 (인용, 임의 변경 금지)

- **런북 장번호 배정**: 8장 백업·복구 = T3 / **9장 로그 상한과 회수 = T4 / 10장 디스크 임계와 회수 레버 = T5(이 문서)** / 11장 회귀 게이트 = T6 / 12·13·14장 = T7. 신설 장은 전부 **기존 마지막 장 뒤, `## 참고` 앞**에 삽입하고 기존 0~7장은 삭제·재배열하지 않는다.
- **공유 심볼 소유권**: `classify_disk()`·디스크 임계 env·`_disk_notify()` = **T5 소유**. `_health_snapshot()` = T1 소유이나 **`disk_high` reason 편입과 그에 따른 `tests/test_health.py` 갱신만 T5 가 수행**(T5 에게 허용된 유일한 T1 테스트 수정 범위). `db_backup_mirror_dir()` = T3 소유(T5 는 호출만, `os.environ` 직접 접근 금지). `slack_notify` 발송 함수 시그니처 = T2 소유(T5 는 어댑터 경유 호출만).

**선행 조건**:
- **T1 `_health_snapshot()` 머지 = 구현 단계 7의 유일한 전제.** T1 미머지 상태에서 착수해도 1~6·8 단계는 전부 진행 가능하며, 7단계만 보류하고 PR 설명에 "T1 머지 후 후속 커밋으로 편입" 을 명시한다. 단 T5 머지는 T1 머지 이후로 미룬다(강제 규칙 5 의 소유권이 T5 에 있으므로 T1 이 고정한 회귀 테스트를 갱신할 주체가 T5 밖에 없다).
- T2 `src/web/slack_notify.py` 머지(08-03~08-05 예정). **미머지여도 T5 는 착수·머지 가능** — 알림 주입은 콜러블 파라미터라 `notify=None` 이면 audit 만 남는다. 단 수용 기준의 `disk_high` Slack 실발화 항목은 T2 머지 이후에만 판정한다.
- T3 `WEB_DB_BACKUP_MIRROR_DIR` 도입(08-05~08-06 예정). 미머지면 미러 대상 판정은 비활성(대상 1개)으로 동작하고, 수용 기준의 "대상 2개" 항목은 T3 머지 후 재확인한다.
- 리베이스 충돌 지점은 `src/web/app.py` 의 `_cleanup_loop`(현재 138행)·`_health_snapshot`(T1 신설)·`admin_metrics`(현재 3224행) 세 곳과 `docs/2026-07-08-ops-deploy-runbook.md` 말미뿐이다.

### 구현 단계

1. **`disk_usage_for(path: Path) -> dict` 신설** (`src/web/maintenance.py`)
   - 현 `disk_usage()`(50~59행)의 본문을 그대로 옮긴다. 인자 경로가 없으면 `path.parent` 로 폴백, `shutil.disk_usage` 의 `OSError` 는 `{}` 반환.
   - `disk_usage()` 는 `return disk_usage_for(audio_store.audio_base())` 한 줄로 축약한다. **반환 키(`total/used/free/percent`)와 실패 시 `{}` 규약은 절대 바꾸지 않는다** — `app.py:3235` 의 `"disk": maintenance.disk_usage()` 와 T1 헬스 스냅샷이 이 스키마에 의존한다.

2. **`disk_targets() -> dict[str, Path]` 신설**
   - `{"data": audio_store.audio_base()}` 를 기본으로 한다.
   - 미러 대상은 **반드시 `db_backup_mirror_dir()` 를 경유**한다(강제 규칙 6 — `os.environ` 직접 접근 금지). T3 의 계약상 미설정이면 `None`, 설정이면 `Path` 다.
     ```
     mirror = db_backup_mirror_dir()          # T3 소유 함수. None = 미러 비활성
     if mirror is not None and mirror.exists():
         targets["mirror"] = mirror
     ```
     - **T3 미머지 상태로 T5 를 먼저 머지해야 하는 경우에만** `maintenance.py` 에 T3 와 **동일 시그니처·동일 본문**의 `db_backup_mirror_dir()` 를 신설한다: `os.environ.get("WEB_DB_BACKUP_MIRROR_DIR", "").strip()` 이 빈 문자열이면 `None`, 아니면 `Path(...)`. T3 리베이스 시 T3 의 정의를 남기고 T5 의 중복 정의를 제거한다.
     - 어느 경우에도 `disk_targets()` 본문에서 `os.environ` 을 직접 읽지 않는다(`os.environ["..."]` 는 미설정 시 `KeyError` 라 현재 상태에서 즉시 예외다).
   - **같은 파티션 중복 제거**: 각 대상의 `os.stat(p).st_dev` 를 비교해 동일 device 면 뒤에 온 대상을 제외한다(미러가 실수로 DATA_DIR 안에 잡혔을 때 같은 파티션으로 알림이 2배 나가는 것을 막는다). `st_dev` 조회 실패(`OSError`)는 중복 제거를 포기하고 대상을 유지한다.
   - 호스트 docker 데이터 루트(`/var/lib/docker`)는 컨테이너에 마운트돼 있지 않아 관측 불가 — **대상에 넣지 않는다**. 이는 T2b 하트비트 스크립트 담당임을 docstring 에 명시한다.

3. **`classify_disk(percent: float, warn: float, error: float) -> str` 신설**
   - `"error"`(percent >= error) / `"warn"`(percent >= warn) / `"ok"`. `error < warn` 로 잘못 설정된 경우 `error = max(error, warn)` 로 보정하고 그 사실을 `observability.audit("disk.threshold_invalid", ...)` 로 1회 기록.
   - 이 함수는 `run_disk_check`·`admin_metrics`·`_health_snapshot` 세 소비자가 공유하는 **유일한 임계 판정 지점**이다. 다른 곳에서 퍼센트 비교를 재구현하지 않는다.

4. **증가율 이력 — JSON 파일 방식** (DB 스키마 변경 없음)
   - `disk_history_path(store) -> Path` = `Path(store.db_path).parent / "disk-history.json"`. `db_backup_dir(store)` 와 동일하게 store 인스턴스 기준이라 테스트가 임시 DB 로 격리된다.
   - `record_disk_sample(store, name: str, used: int, total: int) -> None`: `{"name": ..., "ts": <UTC epoch float>, "used": ..., "total": ...}` 를 append. 파일은 `{"samples": [...]}` 형태. 대상별로 최근 `DEFAULT_DISK_HISTORY_KEEP`(기본 180) 개만 유지.
   - **파일 파손·권한 오류는 전부 삼킨다**: `json.JSONDecodeError`/`OSError` 시 `observability.audit("disk.history_error", error=type(e).__name__)` 후 빈 이력으로 계속 진행. 이력 실패가 임계 판정을 막으면 안 된다.
   - `disk_growth(store, name: str, *, min_span_hours: float = 6.0) -> dict`: 해당 name 의 최신·최오래 샘플로 `bytesPerDay = (used_new - used_old) / span_days` 계산. 반환 `{"bytesPerDay", "gbPerMonth", "daysLeft", "samples", "spanHours"}`.
     - 샘플이 2개 미만이거나 span 이 `min_span_hours` 미만이면 `{"samples": n, "spanHours": h}` 만 채우고 나머지는 `None`(추정치를 지어내지 않는다).
     - `bytesPerDay <= 0` 이면 `daysLeft = None`(감소 중이면 소진일 없음). 양수면 `daysLeft = round(free / bytesPerDay, 1)`.
     - `gbPerMonth = round(bytesPerDay * 30 / 2**30, 2)`.

5. **`run_disk_check(store, *, warn_percent, error_percent, notify=None) -> dict` 신설**
   - `disk_targets()` 를 순회하며 대상마다:
     - `du = disk_usage_for(path)`.
     - **`du` 가 빈 dict 인 경우(측정 실패)**: `observability.audit("disk.measure_failed", target=name, level="WARN")` 를 기록하고 그 대상을 건너뛴다. `notify` 는 호출하지 않는다(측정 실패로 Slack 을 때리면 소음이 된다 — audit 로만 관측).
     - 정상이면 `record_disk_sample`, `classify_disk` 실행. `observability.audit("disk.check", target=name, percent=..., level=level)`.
     - `level in ("warn", "error")` 이면 `observability.audit("disk.high", target=name, percent=..., level=level, free=...)` 후, `notify` 가 있으면 아래 이벤트 dict 로 1회 호출.
   - **notify 계약(T2 와의 결합 지점)**: `run_disk_check` 는 T2 모듈을 임포트하지 않는다. 인자 `notify: Callable[[dict], None] | None` 를 받아 다음 dict 를 넘긴다.
     ```
     {"event": "disk_high",
      "severity": "ERROR" | "WARN",
      "key": f"disk_high:{name}:{level}",     # 쿨다운 키. level 을 키에 포함해 warn->error 승격은 쿨다운을 통과한다
      "target": name, "path": str(path),
      "percent": 87.4, "freeBytes": 12345, "totalBytes": 67890,
      "growth": {...disk_growth 결과...}}
     ```
   - `notify` 호출은 `try/except Exception` 으로 감싸 실패를 삼키고 `observability.audit("disk.notify_error", error=type(e).__name__)` 만 남긴다(알림 실패가 스케줄러를 죽이면 안 된다).
   - 반환값: `{"targets": {name: {"percent":..., "level":...}}, "notified": <int>}`.

6. **`app.py` 배선**
   - env(`CLEANUP_ENABLED` 89행 근처):
     ```
     DISK_CHECK_ENABLED = os.environ.get("WEB_DISK_CHECK_ENABLED", "1") != "0"
     DISK_WARN_PERCENT = float(os.environ.get("WEB_DISK_WARN_PERCENT", str(maintenance.DEFAULT_DISK_WARN_PERCENT)))
     DISK_ERROR_PERCENT = float(os.environ.get("WEB_DISK_ERROR_PERCENT", str(maintenance.DEFAULT_DISK_ERROR_PERCENT)))
     ```
   - `_disk_notify(ev: dict) -> None` 어댑터를 `app.py` 에 둔다. 내부에서 `from src.web import slack_notify` 를 **함수 안에서 지연 임포트**하고 `ImportError` 면 즉시 return(T2 미머지 상태에서도 임포트 에러 없이 동작). T2 모듈의 실제 발신 함수 시그니처(= T2 소유)가 확정되면 이 어댑터 한 곳만 맞춘다.
   - `_cleanup_loop`(138행) 수정: 기존 `if CLEANUP_ENABLED:` 블록과 `_purge_finished_jobs` 블록은 그대로 두고, `await asyncio.sleep(CLEANUP_INTERVAL_SEC)`(163행) **직전**에 다음을 추가한다.
     ```
     # CLEANUP_ENABLED 게이트 밖 — 디스크 정리를 꺼도(WEB_CLEANUP_ENABLED=0) 임계 알림은 계속 돈다.
     if DISK_CHECK_ENABLED:
         try:
             await asyncio.to_thread(
                 maintenance.run_disk_check, store,
                 warn_percent=DISK_WARN_PERCENT,
                 error_percent=DISK_ERROR_PERCENT,
                 notify=_disk_notify,
             )
         except Exception:  # noqa: BLE001 — 한 사이클 실패가 스케줄러를 죽이지 않게 격리
             traceback.print_exc()
     ```
     들여쓰기가 `if CLEANUP_ENABLED:` 안으로 들어가지 않았는지 반드시 확인한다(설계 근거: 정리 배치를 꺼도 디스크 알림은 유지).
   - `lifespan`(182행~)의 `scheduler.start` audit(196행)에 `disk_check=DISK_CHECK_ENABLED` 필드를 추가한다.
   - `_disk_target_view()` 헬퍼를 `admin_metrics` 위에 신설한다(측정 실패 대상 처리를 한곳에 모은다):
     ```
     def _disk_target_view() -> dict:
         """관리자 메트릭용 대상별 디스크 스냅샷 + 임계 판정. 측정 실패 대상은 level='unknown'."""
         out: dict[str, dict] = {}
         for name, p in maintenance.disk_targets().items():
             du = maintenance.disk_usage_for(p)
             if not du:
                 out[name] = {"path": str(p), "level": "unknown"}
                 continue
             out[name] = du | {
                 "path": str(p),
                 "level": maintenance.classify_disk(du["percent"], DISK_WARN_PERCENT, DISK_ERROR_PERCENT),
             }
         return out
     ```
     `du | {...}` 는 새 dict 를 만들 뿐 `disk_usage_for` 의 반환값을 변조하지 않는다(원본 dict 에 키를 써 넣는 형태를 쓰지 말 것).
   - `admin_metrics`(3224행) 응답에 추가 — 기존 `disk` 키는 **그대로 둔다**(프론트·기존 테스트 호환):
     ```
     "diskThresholds": {"warnPercent": DISK_WARN_PERCENT, "errorPercent": DISK_ERROR_PERCENT, "enabled": DISK_CHECK_ENABLED},
     "diskTargets": _disk_target_view(),
     "diskGrowth": {name: maintenance.disk_growth(store, name) for name in maintenance.disk_targets()},
     ```

7. **`_health_snapshot()` 에 `disk_high` reason 편입** (강제 규칙 5 — T1 소유 함수에 대한 T5 의 유일한 수정)
   - `src/web/app.py` 의 `_health_snapshot()`(T1 신설) 안, `disk` 필드를 채우는 지점 **뒤**에 다음을 넣는다. 지역 변수명이 T1 구현과 다르면 이름만 맞춘다.
     ```
     _du = snap.get("disk") or {}
     if _du.get("percent") is not None and maintenance.classify_disk(
         _du["percent"], DISK_WARN_PERCENT, DISK_ERROR_PERCENT
     ) == "error":
         reasons.append("disk_high")     # T1 이 예약어로 명시해 둔 문자열
     ```
   - **판정 기준은 `error` 임계(기본 90) 하나뿐이다.** `warn`(80) 은 Slack 알림 전용이며 health 를 degraded 로 만들지 않는다 — health 는 사람이 즉시 손대야 하는 상태만 표시한다.
   - `disk_high` 는 status 를 `degraded` 로 올린다. 이미 `error`(= `db_write_failed`)인 스냅샷의 status 는 덮지 않는다.
   - 대상은 `maintenance.disk_usage()`(DATA_DIR 파티션) **1개로 한정**한다. `/api/health` 는 무인증 공개 경로가 감싸는 함수라 호출당 stat 을 늘리지 않는다. 미러 임계는 `run_disk_check` 의 Slack 경로가 담당한다.
   - `disk_usage()` 가 `{}` 이면 reason 을 추가하지 않는다(측정 실패를 장애로 승격시키지 않는다).
   - **`tests/test_health.py` 갱신** — T1 이 고정한 "`disk_usage` 가 `{"percent": 99}` 를 반환해도 `reasons` 에 `disk_high` 가 없다" 케이스를 아래 3케이스로 교체한다. 이 파일의 다른 케이스는 건드리지 않는다.
     - `{"percent": 99}` -> `"disk_high" in reasons` 且 `status == "degraded"`
     - `{"percent": 85}` -> `"disk_high" not in reasons`(warn 은 health 에 반영하지 않음)
     - `{}` -> `"disk_high" not in reasons` 且 `GET /api/health` 가 500 이 아님(T1 케이스 그대로 보존)

### 하위호환 / 롤백

- `disk_usage()` 의 시그니처·반환 스키마·실패 시 `{}` 규약은 불변. `GET /api/admin/metrics` 의 기존 `disk` 키도 불변이며 신규 키(`diskThresholds`/`diskTargets`/`diskGrowth`)만 추가된다 — 프론트와 `tests/test_observability_cleanup.py` 의 기존 단언은 그대로 통과해야 한다.
- `_health_snapshot()` 변경은 `reasons` 리스트에 문자열 1개를 **추가**하는 것뿐이다. 공개 `/api/health` 의 키 구성은 그대로이며, `disk`·`schedulers` 를 공개 응답에서 제외한 T1 의 투영 규칙도 건드리지 않는다. 롤백 시 이 블록과 `tests/test_health.py` 의 3케이스를 함께 되돌리면 T1 상태로 정확히 복귀한다.
- DB 스키마 변경 없음(이력은 `<db_path>/../disk-history.json` 파일). 따라서 롤백 시 마이그레이션 되돌림이 없고, 남은 JSON 파일은 구버전이 읽지 않으므로 무해하다.
- 신규 env 3종은 전부 기본값이 있어 `.env.deploy` 를 수정하지 않아도 기존과 동일하게 동작한다(임계 판정이 켜지지만 80% 미만이면 audit 1줄만 늘고 알림은 없다).
- `WEB_DISK_CHECK_ENABLED=0` 이 코드 수정 없이 **주기 판정·알림**을 끄는 킬스위치다. 단 `_health_snapshot` 의 `disk_high` 는 이 스위치와 무관하게 동작한다(health 는 상태 표시이지 발송이 아니다) — 이것까지 끄려면 브랜치 revert.

- `run_disk_check` 는 모든 예외(측정·이력·알림)를 삼키고 audit 만 남긴다 — 어떤 경우에도 `_cleanup_loop` 와 잡 GC 를 죽이지 않는다.

### 막히면

- **T1 이 아직 머지되지 않아 `_health_snapshot()` 이 없는 경우**: 구현 단계 7만 보류하고 나머지를 머지한다. `app.py` 의 라우트 `health()` 본문에 디스크 판정을 직접 박지 말 것 — T1 이 추출할 함수와 판정 소스가 갈려 "진실 둘" 이 된다. 보류 사실을 PR 설명과 인계 노트에 남기고 T1 머지 직후 후속 커밋으로 편입한다.
- **T2 `slack_notify` 의 발신 함수 시그니처가 위 notify 계약(dict 1개 인자)과 다를 때**: 시그니처 소유자는 T2 다. `maintenance.run_disk_check` 는 건드리지 말고 `app.py` 의 `_disk_notify` 어댑터만 고친다. 어댑터로도 쿨다운 키를 전달할 수단이 없으면(예: T2 가 키를 내부 생성) 에스컬레이션 — WARN/ERROR 승격 시 쿨다운을 통과시킬지가 사람 판단 대상이다.
- **T3 의 `db_backup_mirror_dir()` 시그니처가 다를 때**: 소유자는 T3 다. `disk_targets()` 의 호출부만 맞추고, 어떤 경우에도 `os.environ` 직접 접근으로 우회하지 않는다.
- **미러 경로가 DATA_DIR 과 같은 파티션으로 밝혀진 경우**: T3 의 백업 이중화 목적(볼륨 사고 내성) 자체가 무효화된다. 코드로 우회하지 말고 사용자에게 별도 마운트 확보 여부를 확인한다.
- **런북에 이미 `## 10.` 이 있거나 T3·T4 가 배정 밖 번호를 선점한 경우**: 번호를 임의로 밀지 말고 즉시 에스컬레이션한다. 배정표(8=T3 / 9=T4 / 10=T5 / 11=T6 / 12~14=T7)는 전역 계약이며 T5 가 단독으로 바꿀 수 없다.
- **임계 기본값 80/90 이 라이브 현황과 어긋나는 경우**(예: D1 지표에서 이미 85% 초과): 08-03 지표 리뷰 게이트에서 확정하기로 한 사항이다. 에이전트가 임의로 낮추거나 올리지 말고 그 수치를 제시해 사용자 결정을 받는다.
- **`diskGrowth.daysLeft` 가 30일 미만으로 나오는데 회수 레버 3개로 부족한 경우**: 남은 레버는 오디오 원본 정리뿐이며 이는 unresolved-4(오디오 백업·정리 정책) 미결정 사항이다. **삭제 코드나 삭제 명령을 실행하지 말고** 현황 수치(`du -sh` 결과, daysLeft)를 붙여 사용자 결정을 요청한다. `meetings.db` 무백업 prune 사고 전례가 있는 저장소다.
- **`WEB_AUDIT_LOG` 미설정으로 `disk.high` audit 이 stdout 에만 남아 라이브에서 추적이 어려운 경우**: unresolved-6(WEB_AUDIT_LOG 활성화 여부)에 걸린 사안이다. T5 에서 임의로 켜지 말고 `docker logs` 기반 확인으로 판정한다.
