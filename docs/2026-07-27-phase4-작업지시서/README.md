## 2. 합의된 목표

### G1. 라이브(:49152)를 릴리스 태그와 동일한 코드로 올리고, 그 사실을 사람 증언이 아니라 기계 판정으로 증명한다.

**측정**: curl -k https://<host>:49152/api/health 응답의 backendSha·frontendSha 가 release/phase4-w1 태그의 두 저장소 커밋 SHA 와 문자열 일치. 확장 스모크 9항목(로그인, e2e, Google 3종, Jira 다이얼로그+이슈생성 1건, 잡 취소 1건, Slack 봇 명령 1개, Docs 템플릿 1건, admin 진단 2종) 각각 pass/fail 기록 파일 1개 확보.

### G2. 프로세스가 죽어도 사람에게 도달하는 알림 경로를 만든다 — 인프로세스 알림과 프로세스 외부 하트비트의 이중 구조.

**측정**: (a) docker kill 로 컨테이너를 죽인 상태에서 외부 하트비트가 Slack 알림 1건 발송(수신 스크린샷). (b) 인프로세스 4종(stt_stalled·cred_invalid·backup_failed·disk_high) 전부 단위테스트 통과, 그중 backup_failed·cred_invalid 2종은 라이브 실수신. (c) 웹 프로세스 재기동 후 동일 이벤트키 재발송 0건(쿨다운 영속 확인).

### G3. 백업이 컨테이너 재생성과 볼륨 사고를 견디고, 복구가 DB 뿐 아니라 자격증명까지 되살린다.

**측정**: (a) docker compose up -d --build 재생성 후 호스트 미러 경로에 스냅샷 파일 잔존. (b) 미러에서도 keep 초과분 삭제 확인(파일 개수). (c) 복구 리허설에서 복원본 users 수 == 원본 수 AND 자격증명 1건 verify 결과가 decrypt_failed 아님 AND 회의 1건 조회 성공. (d) 시크릿 3종(JWT_SECRET·CRED_ENC_KEY·SLACK_BOT_TOKEN) 오프호스트 사본 존재 확인.

### G4. 무인 방치 시 누적형 리스크(docker 로그·디스크)가 상한 안에 머물고, 임계 도달 시 사람이 실행할 회수 레버가 존재한다.

**측정**: (a) compose 3개 서비스(meetscript·slackbot·caddy) 전부 max-size·max-file 적용 후 docker inspect --format '{{.LogPath}}' | xargs du -sh 값이 max-size*max-file 이하. (b) 임계 강제 하향(WARN 1%)으로 disk_high 알림 1건 발화. (c) disk_usage() 가 빈 dict 를 반환하는 경우에도 WARN audit 1건 기록됨(단위테스트). (d) 런북에 회수 명령블록(대상 경로·판정 기준·복사 가능한 명령)이 있고 사용자가 1회 실행 성공.

### G5. 회귀 게이트가 사람 기억이 아니라 자동 실행에 의존한다(수단은 클라우드 CI·self-hosted·pre-push 중 결정 결과에 따름).

**측정**: 일부러 ruff 또는 pytest 를 실패시킨 커밋이 머지/푸시되지 못함을 1회 실증(required status check 404 -> 설정 완료 후 재확인, 또는 훅 차단 로그). 게이트 스코프는 ruff check src tests == 0 errors, pytest 367건 통과.

### G6. 배포·검증·복구·롤백을 런북만으로 재현할 수 있게 만들고, 알림에 대응 주체를 붙인다.

**측정**: 지명된 1인이 런북만 보고 (a) 롤백(직전 SHA 태그 이미지로 기동 후 health 200) 1회, (b) 복구 리허설 1회를 실제 수행 성공. 각 알림 메시지에 런북 대응 섹션 링크와 1차 대응자·대체자 이름이 포함됨.

## 4. 사람이 결정해야 할 것 (미해결)

에이전트가 대신 정할 수 없어 남긴 항목이다. 괄호 안은 이 결정이 막고 있는 작업이다.

| 주제 | 왜 사람이 결정해야 하는가 |
|---|---|
| LB_Note 저장소 공개(public) 유지 여부 | 저장소 공개는 조직의 오픈소스/보안 정책 사안이지 기술 판단이 아니다. 게다가 이 결정이 T6 의 러너 선택지를 좌우하므로(공개 상태에서 self-hosted 러너는 fork PR 이 라이브 DB·모델·시크릿이 있는 171 호스트에서 임의 코드를 실행할 수 있게 만든다) 07-28 에 답이 필요하다. |
| 운영 LLM 자격증명 경로 — 요약/액션을 무엇으로 돌릴 것인가 | 비용 집행과 약관 리스크 수용은 결재 사항이다. 에이전트가 대신 정할 수 없다. Phase 4 에서는 T1b 스모크 3번의 통과 조건이 여기에 걸리므로, 미결정이면 '라이브 계정 1개에 개인 토큰 등록 후 1회 성공'이라는 임시 증거만 남고 Phase 5 진입 판정이 미뤄진다. 대체 판정 기준은 이미 T1b 에 명시해 P0 가 무기한 열리지 않게 했다. |
| 회귀 게이트 실행 수단 — 사내 코드를 어디서 돌릴 것인가 | 사내 코드 반출은 회사 정책이고 회신 리드타임을 에이전트가 통제할 수 없다. 그래서 3주차가 아니라 07-28 에 질의를 발신하고 08-03 결정 기한을 두는 형태로만 처리했다. unresolved-1 의 결과에 종속된다. |
| 회의 원본 오디오의 백업·정리 정책 | 무엇을 잃어도 되는가는 데이터 소실 리스크의 수용 주체가 정할 문제다. 또 이 결정이 T5 의 회수 명령블록 내용(무엇을 지워도 되는가)과 T3 미러 마운트의 용량 요구를 동시에 결정한다. 미결정이면 T5 는 알림만 늘리고 관리자는 수동 삭제 판단 근거가 없다. |
| 주당 실작업 가용시간과 예산 초과 시의 조치 | 본인의 실제 가용 시간은 본인만 안다. 사용자가 T1~T7 전부 유지와 3주를 확정했으므로 삭감 후보 사전 지정은 기각했고, 대신 예산 초과 시 첫 조치를 '실환경 검증 -> 단위테스트 검증으로 하향'으로 두었다. 어느 전제인지 확정돼야 08-03 중간 점검에서 지연 여부를 판정할 수 있다. |
