## T0. 릴리스 전제 정리 및 시크릿 위생

**목표**: PUBLIC 저장소에서 배포 시크릿 파일(`deploy/.env.deploy`)이 `git add -A` 한 번에 커밋되는 경로를 `.gitignore` 규칙으로 영구 차단하고, 이미 커밋된 민감정보(실 IP·공용 초기 비번·사내 PII)의 노출 범위를 기계 판정으로 확정해 Phase 4 의 첫 라이브 배포(D1 = 07-30) 전에 전제를 정리한다.

**우선순위 / 예상 공수**: P0 / 에이전트 2~3h + [사용자 수행] 30분~1h (07-28 오전 반나절 이내, Phase 4 최선행)

**선행 조건**: 없음. (역으로 T1·T3 이 이 브랜치의 머지를 선행 조건으로 참조한다. 이 지시서는 Phase 4 에서 가장 먼저 머지되어야 한다.)

**브랜치**: `feature/171-secret-hygiene` -> PR -> main. 커밋 메시지에 Jira 키를 포함한다. Atlassian MCP 가 끊겨 있어 에이전트가 키를 조회할 수 없으므로, **커밋 직전에 사용자에게 태스크 키를 물어 받는다**(추측 금지). 연관 태스크가 없다는 답도 정상 케이스로 처리한다.

### 구현 단계

1. **`.gitignore` 에 배포 시크릿 규칙 추가.** 파일 맨 끝에 아래 4줄을 그대로 덧붙인다. 순서가 중요하다 — negation(`!`)은 반드시 와일드카드 뒤에 와야 한다.

   ```
   # 배포 시크릿 실값 (호스트 배포 repo 에서 생성 — 커밋 금지). example 만 예외로 추적.
   deploy/.env.deploy
   deploy/.env.deploy.*
   !deploy/.env.deploy.example
   ```

   근거(실측): 현재 `git check-ignore -q deploy/.env.deploy` 의 rc 는 1(= 무시되지 않음)이고 저장소는 PUBLIC(`gh repo view --json isPrivate` -> `false`)이다. 호스트 배포 repo 에서 `git add -A` 를 한 번 하면 `JWT_SECRET`·`CRED_ENC_KEY`·`SLACK_BOT_TOKEN` 실값이 공개 커밋된다. 이 컨테이너에는 `deploy/.env.deploy` 파일 자체가 없지만 **파일이 없어도 규칙 매치는 `git check-ignore` 로 검증 가능**하므로 수용 기준은 그 방식으로 판정한다(별도 임시 파일 생성 불필요).

   주의: `deploy/.env.deploy.example` 은 이미 tracked 라 gitignore 의 영향을 받지 않는다. 그래도 negation 을 명시해 두는 이유는, 이 파일이 향후 어떤 이유로 untracked 상태가 되었을 때(재생성·리네임) 조용히 사라지는 것을 막기 위해서다.

2. **이미 커밋된 민감정보 스캔.** 저장소 루트에서 아래 5개 명령을 그대로 실행하고, 출력 전문을 `T0-secret-scan.md` 에 붙인다. 괄호 안은 이번 감사에서 실측한 baseline(2026-07-27 기준)이며, 이보다 늘었다면 새로 유입된 것이므로 즉시 보고한다.

   ```
   git grep -nE "121\.125\.78\.171" -- .                                   # 실 IP (9건)
   git grep -nE "axlead1234" -- .                                          # 공용 초기 비번 (5건)
   git grep -nE "lbnote\.litbig\.com" -- .                                 # 사내 FQDN (5건)
   git grep -nE "xox[baprs]-[A-Za-z0-9-]{10,}|sk-ant-[A-Za-z0-9_-]{10,}|AIza[A-Za-z0-9_-]{20,}|ghp_[A-Za-z0-9]{20,}|BEGIN [A-Z ]*PRIVATE KEY" -- .   # 실토큰/개인키 (0건)
   git grep -nE "@litbig\.com" -- .                                        # 사내 이메일 (config/participants.json 55건 외 docs 2 / tests 16)
   ```

   판정 기준:
   - 4번(실토큰·개인키) 결과가 **0건이 아니면 즉시 작업을 중단**하고, 치환이 아니라 **자격증명 회전(rotate)** 을 최우선으로 사용자에게 에스컬레이션한다. 현재 0건이며 `deploy/.env.deploy.example` 의 `xoxb-CHANGE_ME`·`CHANGE_ME_FERNET_KEY` 는 전부 플레이스홀더다.
   - 5번의 `tests/` 히트(`hong@`, `svc@`, `none@`)와 `tests/test_jira_client.py` 의 `SECRET-TOKEN` 은 합성 픽스처이므로 치환 대상이 아니다. 건드리면 테스트가 깨진다.

3. **히스토리 노출 여부 확정(사실 확인만, 재작성은 범위 밖).** 아래를 실행해 결과를 보고서에 남긴다.

   ```
   git log --all --oneline --diff-filter=A -- 'deploy/.env.deploy'
   git log --all --oneline -S '121.125.78.171' -- . | head -20
   git log --all --oneline -S 'axlead1234' -- . | head -20
   ```

   실측 결과(이번 감사): 첫 명령의 출력은 **0행** — 즉 `deploy/.env.deploy` 는 이 저장소 히스토리에 한 번도 추가된 적이 없고, 시크릿 3종의 실값은 아직 공개되지 않았다. 1단계는 사고 예방이지 사후 수습이 아니다. 이 사실을 보고서에 명시한다.

   반대로 실 IP·공용 비번·사내 FQDN 은 **이미 과거 커밋에 존재**하므로, 4단계의 현재 파일 치환만으로는 과거 커밋에서 여전히 조회된다. 히스토리 재작성(`git filter-repo` / BFG + force-push + 전 클론 재동기)은 **이 지시서의 범위 밖**이다. 보고서에는 (a) 노출된 값 목록, (b) 노출 창(최초 커밋일~현재), (c) 실효 완화책 후보 3가지 — 저장소 private 전환 / 히스토리 재작성 / 값 자체 변경(IP·포트 변경, 초기 비번 정책 변경) — 만 적고 **선택은 사용자 결정으로 남긴다**.

4. **(조건부) 플레이스홀더 치환.** unresolved-1 이 "(B) 공개 유지"로 확정된 경우에만 실행한다. 변경 대상 표의 조건부 행을 순서대로 처리하되:
   - 치환 토큰은 `<DEPLOY_HOST_IP>`, `<DEPLOY_HOST_FQDN>`, `<초기비번>` 세 가지로 통일한다(문서마다 다른 표기 금지).
   - 런북(`docs/2026-07-08-ops-deploy-runbook.md`)의 `ssh evan@...`·`curl -k https://...:49152/api/health` 같은 **복사해 쓰는 명령줄**은 토큰만 바꾸고 명령 구조는 그대로 둔다. 명령 위에 "실 호스트 값은 `.env.deploy` 의 `SITE_HOST` 를 참조" 한 줄을 덧붙인다.
   - `docs/2026-07-08-ops-deploy-runbook.md:240~251` 의 `172.17.0.2` 는 Docker 기본 브리지 대역 설명이라 민감정보가 아니다. 치환하지 않는다.
   - `tools/bulk_create_users.py` 의 default 제거는 CLI 동작 변경이다. docstring 실행 예시(5·13행)를 같은 커밋에서 함께 고쳐, 문서만 보고 실행했다가 실패하는 상태를 만들지 않는다.

5. **PII 노출 보고(조치 아님).** 아래 2건은 저장소가 PUBLIC 인 동안 사내 정보가 그대로 공개된다. 에이전트가 임의로 삭제·치환하지 말고 보고서에 사실과 영향만 적어 **사용자 결정(unresolved 상신)** 으로 남긴다.
   - `config/participants.json` — 실명·직함·사내 이메일 55행. 소비처는 `tools/bulk_create_users.py` 하나뿐이므로(`git grep -n participants.json` 로 확인) 파일을 untrack + gitignore 하고 호스트에만 두는 대안이 기술적으로 가능하다. 단 소비처가 일회성 스크립트라 영향은 작다.
   - `answer/ax_tf_클로바.txt` — 실 사내 회의 전사(참석자 실명 포함). 현재 `.gitignore` 주석에 "회의 정답 transcript 1건은 소유자 판단으로 포함"이라 명시돼 있어 **의도적 포함**이다. 뒤집지 말고 "공개 유지 결정 시 재검토 대상"으로만 올린다.

6. **[사용자 수행] 호스트 배포 repo 에서 `.env.deploy` 가 untracked 인지 확인.** 이 컨테이너에는 호스트 SSH 키가 없어 에이전트가 대신 실행할 수 없다. 사용자가 호스트에서 아래를 실행하고 출력을 회신한다.

   ```
   cd /home/evan/LB_Note-deploy
   git status --short --branch
   git ls-files --error-unmatch deploy/.env.deploy ; echo "ls-files rc=$?"   # rc=1 이어야 정상(추적 안 됨)
   git check-ignore -q deploy/.env.deploy ; echo "check-ignore rc=$?"        # T0 머지+pull 후 rc=0 이어야 정상
   ```

   판정: `ls-files rc=1` AND (T0 머지 반영 후) `check-ignore rc=0`. 만약 `ls-files rc=0`(= 이미 추적 중)이면 **`.gitignore` 만으로는 해결되지 않는다**. 이때는 `git rm --cached deploy/.env.deploy` 후 커밋이 필요하고, 원격에 이미 푸시됐다면 시크릿 3종 전량 회전이 선행이다. 즉시 에스컬레이션한다.

7. **[사용자 수행] 프론트엔드 저장소의 미머지 커밋 확인.** 프론트 저장소는 이 컨테이너에 없으므로 에이전트는 **확인 방법만** 제공한다. 특정 커밋 SHA 를 단정하지 않는다(1차 산출물에 나온 SHA 는 이 환경에서 검증 불가하므로 인용하지 않는다). 사용자가 프론트 저장소 작업 경로(메모상 `/home/evan/LB_Note-web`, 다르면 실제 경로)에서 실행한다.

   ```
   git fetch origin --prune
   git status --short --branch
   git branch --no-merged origin/main -vv          # main 에 안 들어간 로컬 브랜치 목록
   git log --oneline origin/main..HEAD             # 현재 브랜치의 미머지 커밋
   git log --oneline --all --not --remotes         # 원격 어디에도 없는 커밋(= 푸시 자체가 안 된 것)
   ```

   회신받을 것: (a) 미머지 커밋의 SHA·제목·브랜치명, (b) 그 커밋이 Jira 기본 프로젝트/등록 UX 변경을 포함하는지, (c) 푸시 -> PR -> main 머지 완료 시각. 이 결과를 T1 의 스모크 항목 중 **Jira 다이얼로그 기본 프로젝트 선택** 항목의 선행 조건 충족 여부로 사용한다. 미머지 상태로 D1 배포에 들어가면 해당 스모크 항목은 설계상 실패가 예정돼 있으므로, 머지 불가 시 T1 에 "해당 항목 N/A + 사유" 를 사전 기록한다.

8. **unresolved 상신 문안 작성.** 보고서 끝에 사용자 결정이 필요한 항목을 선택지 형태로 정리한다. 에이전트가 임의로 결정하지 않는다.
   - unresolved-1 저장소 공개(PUBLIC) 유지 여부 — (A) private 전환: 실 IP·초기 비번·토폴로지가 즉시 가려지고 T6 에서 self-hosted 러너(171) 사용 가능. (B) 공개 유지: 4단계 치환 실행 + T6 는 클라우드 러너만(self-hosted 금지). 어느 쪽이든 1단계는 무조건 선행. **회신 기한 07-28**(T6 러너 선택이 여기에 종속).
   - PII 2건(`config/participants.json`, `answer/ax_tf_클로바.txt`)의 공개 유지 여부.
   - 히스토리에 이미 남은 실 IP·초기 비번에 대한 조치 수준(무조치 / 값 변경 / 히스토리 재작성).

### 하위호환 / 롤백

- `.gitignore` 추가는 **이미 추적 중인 파일에 아무 영향이 없다**(git 은 tracked 파일에 ignore 규칙을 적용하지 않는다). `deploy/.env.deploy.example` 은 tracked 이므로 계속 정상 추적되며, negation 줄은 이중 안전장치다. 개발 컨테이너에는 `deploy/.env.deploy` 파일 자체가 없어 동작 변화도 0 이다.
- 실행 코드는 건드리지 않는다. 유일한 동작 변경은 `tools/bulk_create_users.py` 의 `--password` 필수화이며, 이는 일회성 운영 스크립트로 `src/`·`tests/` 어디에서도 import 되지 않는다(`git grep -l bulk_create_users -- src tests` 출력 0행). 기존 실행 습관이 깨지는 대신 공용 비번이 기본값으로 박히는 상태가 사라진다.
- 롤백: 커밋 단위가 분리돼 있으므로 `git revert <치환커밋>` 만으로 문서 치환을 되돌릴 수 있고, `.gitignore` 커밋은 유지된다. 반대로 `.gitignore` 만 되돌릴 이유는 없다(되돌리면 시크릿 커밋 경로가 다시 열린다).
- 파일 충돌 예고: `deploy/.env.deploy.example` 은 T1·T2·T3·T4·T5 가, `docs/2026-07-08-ops-deploy-runbook.md` 는 T3·T4·T5·T6·T7 이 이어서 수정한다. T0 은 실행 순서상 **가장 먼저(07-28)** 머지되므로 뒤 브랜치들이 main 재동기(rebase) 후 작업한다. T0 은 두 파일에서 **문자열 치환만** 하고 새 변수·새 장(`## N.`)을 만들지 않으므로 충돌 표면은 최소다. 런북 장번호 8~14 는 T3~T7 소유이며 T0 은 사용하지 않는다.
