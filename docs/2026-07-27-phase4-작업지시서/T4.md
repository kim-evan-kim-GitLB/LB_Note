## T4. 로그 로테이션 — compose json-file 상한(3서비스) + audit 파일 핸들러 RotatingFileHandler 교체

**목표**: 무인 방치 시 무제한 증식하는 docker json-file 로그에 상한을 걸어 디스크 누적 리스크를 상한 안에 가둔다(라이브 실효 있는 유일한 조치). 부가로 `WEB_AUDIT_LOG` 파일 핸들러를 `RotatingFileHandler` 로 교체하되, 이 항목은 배포본에서 no-op 이므로 단위테스트 통과까지만 요구한다.

**우선순위 / 예상 공수**: P1 / 3~4h (compose 1.5h + 핸들러/테스트 2h). 배포 반영은 D3(08-13 야간) 창에 T5 와 묶어 1회.

**선행 조건**: 없음 (코드 작업은 T1~T3 와 독립. 다만 라이브 반영·로그 실측은 D3 배포 창에서 수행하므로 T1 의 배포 절차가 확립돼 있어야 함)

**브랜치**: `feature/171-log-rotation`

**런북 장번호 배정(전 지시서 공통, 대필·선점 금지)**: 8장 백업·복구 = T3 / **9장 로그 상한과 회수 = T4(이 지시서)** / 10장 디스크 임계와 회수 레버 = T5 / 11장 회귀 게이트 = T6 / 12장 배포 스모크 = T7 / 13장 롤백 = T7 / 14장 알림 이벤트 사전 = T7. 신설 장은 전부 **기존 마지막 장 뒤, `## 참고` 앞**에 삽입하고 기존 0~7장은 삭제·재배열하지 않는다. 착수 시점 실측 런북은 `## 0.`~`## 7.` + `## 참고`(278행)이므로, T3 미머지 상태로 T4 가 먼저 들어가도 **번호는 9 를 유지**한다(8장 자리는 T3 몫으로 비워 둔다 — 번호를 당겨 쓰지 말 것).

### 구현 단계

1. **브랜치 생성**: `git fetch origin && git checkout -b feature/171-log-rotation origin/main`. (현재 브랜치 `feature/171-jira-projects-default` 에서 이어가지 말 것 — 다중 세션 공유 작업트리이므로 착수 직전 `git status --short --branch` 로 브랜치 확인)

2. **compose logging 추가**: `deploy/docker-compose.yml` 의 세 서비스 각각에 `logging:` 블록 추가. 배치 위치는 각 서비스의 `restart:` 바로 아래로 통일해 diff 를 읽기 쉽게 한다. 값은 compose 변수 치환(`${LOG_MAX_SIZE:-50m}`)을 쓰되, 기존 파일 상단 주석대로 `--env-file .env.deploy` 없이 기동하면 치환이 안 되므로 **반드시 기본값(`:-`)을 붙여** env 미전달 시에도 상한이 적용되게 한다.

3. **.env.deploy.example 갱신**: `# ----- 호스트측(compose 변수) -----` 섹션 위에 로그 섹션을 추가. `LOG_MAX_FILE` 은 json-file 드라이버가 **문자열 숫자**를 요구하므로 따옴표 처리 주의(compose 옵션 값은 `"${LOG_MAX_FILE:-5}"`).

4. **RotatingFileHandler 교체**: `src/web/observability.py` 의 `_ensure_handler()` 만 수정한다. 다음 4가지 기존 동작을 반드시 보존한다.
   - `WEB_AUDIT_LOG` 미설정/빈문자열 -> 핸들러 부착 없음(현행과 동일, `_handler_ready = True` 로만 마킹).
   - 동일 경로 중복 부착 방지 분기(`isinstance(h, logging.FileHandler)` + `baseFilename` 비교). `RotatingFileHandler` 는 `FileHandler` 의 서브클래스라 이 isinstance 검사는 그대로 유효하다 — **검사 조건을 바꾸지 말 것**.
   - 포매터 문자열 `"%(asctime)s %(message)s"` 불변(감사 로그 파싱 호환).
   - `OSError` 를 삼키고 stdout(propagate)만으로 진행하는 폴백 유지.

5. **테스트 작성** (`tests/test_audit_log_rotation.py`). `observability.reset()` 은 핸들러 상태를 건드리지 않으므로, 각 테스트는 fixture/`finally` 에서 `_LOGGER.handlers` 에서 추가한 핸들러를 `removeHandler` + `close` 하고 `observability._handler_ready = False` 로 되돌려 격리한다.
   1. `test_audit_log_unset_attaches_no_handler`: `WEB_AUDIT_LOG` 미설정 상태에서 `audit("x")` 호출 후 `_LOGGER.handlers` 에 `FileHandler` 계열 0개(하위호환 회귀 방지).
   2. `test_rotating_handler_attached_with_env`: tmpdir 경로 지정 시 부착된 핸들러가 `logging.handlers.RotatingFileHandler` 인스턴스이고 `maxBytes == 52428800`, `backupCount == 5`.
   3. `test_rotation_creates_backup_files`: `WEB_AUDIT_LOG_MAX_BYTES=512`, `WEB_AUDIT_LOG_BACKUP_COUNT=2` 로 설정하고 `audit()` 를 수십 회 호출 -> `log`, `log.1`, `log.2` 가 존재하고 `log.3` 은 없음(개수 상한 실증), 각 파일 크기 <= 약간의 여유를 둔 상한.
   4. `test_audit_line_format_unchanged`: 로테이션 적용 후에도 기록된 라인이 `event=meeting.create meeting_id=abc owner=kim` 형태를 포함(포맷 불변). 동시에 `observability.snapshot()["meeting.create"] == 1` 로 카운터 동작 불변 확인.

6. **런북 `## 9. 로그 상한과 회수` 절 추가**: `docs/2026-07-08-ops-deploy-runbook.md` 의 **기존 마지막 장 뒤, `## 참고` 앞**에 `## 9. 로그 상한과 회수` 를 삽입하고 아래를 ASCII 안전 문자로 기재한다. 장번호는 배정표대로 **9 고정**이며, 8/10/11 번은 각각 T3/T5/T6 소유라 T4 가 쓰지 않는다. 삽입 후 아래 두 판정을 반드시 통과시킨다(수용 기준과 동일): `grep -c '^## 9\.' docs/2026-07-08-ops-deploy-runbook.md` -> `1`, `grep -o '^## [0-9]\+\.' docs/2026-07-08-ops-deploy-runbook.md | sort | uniq -d` -> 출력 0줄.
   - 상한 계산: 서비스당 50m x 5 = 250MB, 3서비스 합계 최대 750MB.
   - `[사용자 수행]` 반영 전 실측: `docker ps -q | xargs docker inspect --format '{{.LogPath}}' | xargs -r sudo du -sh`
   - `[사용자 수행]` 반영 후 재측정 및 회수: `logging` 옵션은 **기존 컨테이너에 소급 적용되지 않으므로** `docker compose --env-file .env.deploy up -d --force-recreate` 로 컨테이너를 재생성해야 기존 json 로그 파일이 폐기된다는 사실을 명시.

### 하위호환 / 롤백

- **audit 라인 포맷 불변**: 포매터 `"%(asctime)s %(message)s"` 와 `audit()` 의 `event=... k=v` 직렬화는 손대지 않는다. 수용 기준 테스트 4번이 이를 고정한다.
- **`WEB_AUDIT_LOG` 미설정이 기본 경로**: 배포본·개발 서버 모두 현재 이 변수가 없으므로 코드 변경 후에도 런타임 동작은 **완전히 동일**(파일 핸들러 미부착, stdout propagate 만). 테스트 1번이 이를 고정한다.
- **중복 부착 방지 로직 유지**: `RotatingFileHandler` 는 `FileHandler` 서브클래스이므로 기존 `isinstance` 기반 dedupe 가 그대로 동작한다. reload 시 로그 중복 라인 회귀 없음.
- **`OSError` 폴백 유지**: 권한/경로 문제로 핸들러 부착이 실패해도 웹 프로세스는 기동을 계속한다(기존 동작).
- **compose 롤백**: `logging:` 블록은 순수 가산 변경이라 블록 3개 삭제 + `up -d --force-recreate` 로 즉시 원복. 데이터 영향 없음.
- **소급 미적용 주의**: `logging` 은 컨테이너 생성 시점 설정이라 기존 실행 컨테이너의 로그 파일 크기를 되돌리지 않는다. 반대로 재생성하면 그 시점 json 로그가 사라지므로, 조사 중인 장애가 있으면 재생성 전에 `docker logs > 파일` 로 보존한 뒤 진행할 것.

### 막히면

- **`WEB_AUDIT_LOG` 를 실제로 켤지**는 unresolved-6(감사·규정 요구 사항)이다. 에이전트가 임의로 `.env.deploy.example` 에 추가하지 말고 사용자 결정을 받는다. 미결정이면 코드만 준비된 상태로 T4 를 종료한다(설계 합의대로 **라이브 효과 검증은 완료조건이 아니다**).
- **`LOG_MAX_SIZE` 50m 이 적정한지 판단이 필요하면** D1(07-30) 배포에서 수집하는 라이브 30일 운영 지표 스냅샷의 로그 실측치를 근거로 08-03 지표 리뷰 게이트에서 확정한다. 실측 전에는 50m x 5 를 기본값으로 두고 진행한다.
- **호스트에서 `docker inspect` 결과 상한이 안 붙는 경우**(daemon 기본 로깅 드라이버가 json-file 이 아닌 경우 등)는 `docker info --format '{{.LoggingDriver}}'` 결과를 사용자에게 받아 판단한다. `journald`/`local` 이면 compose 옵션 키가 달라지므로 값 설계를 다시 잡아야 한다 — 이 경우 임의 추정하지 말고 에스컬레이션.
- **docker 명령은 이 컨테이너에서 실행 불가**(`which docker` 결과 없음). 모든 `docker ...` 단계는 `[사용자 수행]` 이며, 에이전트는 명령문과 기대 출력만 제공하고 사용자 회신 결과를 증거로 기록한다.
