## 1. 배경과 결론

"파일 기반 회의 분석"(`FileUploadView`)과 "새 회의 시작(녹음)"(`RecorderView`)이
서로 다른 결과를 만드는 것처럼 보인다는 문제 제기에서 출발했다.

두 경로의 코드를 전수 확인한 결론은 다음과 같다.

- **분석 파이프라인(STT -> 정제 -> 요약 -> 액션추출)은 두 경로가 완전히 동일하다.**
  둘 다 `processMeetingAudio()` -> `POST /api/ai/process` -> 동일 잡 워커를 탄다.
  백엔드에는 경로를 구분하는 코드가 존재하지 않는다.
- 차이는 전부 **프론트의 입력 수집 레이어와 결과 확정 레이어**에 있다.
- 그 차이 중 일부는 명백한 결함(데이터 유실)이고, 일부는 두 화면에 같은 로직이
  복사되어 생긴 표류(drift)다.

따라서 이 설계의 목표는 화면을 합치는 것이 아니라,
**두 화면이 공유해야 할 로직을 한 곳으로 모아 표류를 없애고, 그 과정에서 결함을 제거**하는 것이다.
파일 업로드 화면은 "경량 전사 도구" 성격을 유지한 채 남는다.

| 결과 확정 | 수동 등록 | 자동 저장 | **자동 저장 + 버리기 버튼** |
| 결과 화면 | 자체 미니뷰 + 내보내기 | 없음(바로 ReviewView) | 파일 유지 + **ReviewView 에 내보내기 추가** |
| 재시도 시 staging | 매번 재업로드 | 토큰 캐시로 1회만 | **공용 훅으로 통일** |

## 3. 결함 목록

판정 기준: **결함** = 사용자가 입력했거나 시스템이 확보한 데이터가 소리 없이 사라지는 것.

### D1. googleEventId 유실 (결함, 두 경로 공통)

  `currentMeeting` 을 만들지만, `RecorderView` 의 `onProcessed` 페이로드
  (`src/components/RecorderView.tsx:369`)에도, `handleMeetingProcessed` 의
  `baseMeeting`(`src/App.tsx:369`)에도 해당 필드가 없다.
- 영향: 캘린더 일정에서 녹음을 시작해도 저장된 회의는 원본 이벤트와 연결이 끊긴다.

  **새로 만드는 기능이 처음부터 같은 결함을 안고 태어난다.** 캘린더 작업의 선행 조건.

### D2. date 포맷 불일치 (결함)

- 근거: 파일 경로는 `metadata.date`(`'YYYY-MM-DD'`)를 그대로 전달
  (`src/components/FileUploadView.tsx:459`), 녹음 경로는 ISO 문자열로 변환
  (`src/components/RecorderView.tsx:372`).
- 영향: 같은 필드에 두 가지 포맷이 섞여 영속된다. 현재는 `meetingDate()` 폴백
  (`src/lib/meetingDate.ts`)과 백엔드 `_fill_display_date`(`/app/src/web/app.py:1800`)가
  받아주고 있어 표면화되지 않지만, 정렬/범위 질의를 추가하는 순간 터진다.
  2026-07-16 UX 리뷰에서 이미 `date` 부재로 전 화면이 깨진 전례가 있다.

### D3. 장소(location) 입력 폐기 (결함)

- 근거: 파일 경로가 장소 입력란을 제공하고(`FileUploadView.tsx:317`) 결과 화면에도
  표시하지만(`:448`), `onProcessed` 페이로드(`:454`)에 포함하지 않아 저장되지 않는다.
- 영향: 사용자가 입력한 값이 화면 전환과 동시에 사라진다.
  `Meeting.location` 타입 필드(`src/types.ts:112`)는 이미 존재하고,
  백엔드 `create_meeting` 은 임의 필드를 그대로 영속하므로 백엔드 변경이 필요 없다.

### D4. 파일 경로 참석자 미수집 (기능 격차)

- 근거: `processMeetingAudio(audioBase64, type, [], ...)`(`FileUploadView.tsx:160`)로
  참석자를 빈 배열로 보내고, `onProcessed` 에도 참석자를 싣지 않아
  `handleMeetingProcessed` 의 기본값(호스트 1명)으로 저장된다.
- 영향: 파일 업로드로 만든 회의록은 참석자가 항상 본인 1명이다.
  회의록 발송 대상 선정, Slack DM, Jira 담당자 매핑이 모두 참석자 기반이므로
  후속 연동에서 실질적 손실이 발생한다.
- **주의(오해 방지)**: 백엔드 `ProcessRequest.participants`(`/app/src/web/app.py:355`)는
  수신만 하고 `_run_ai_job` 에서 사용하지 않는다(화자분리 v1 미적용).
  참석자는 STT 결과가 아니라 **회의 레코드 메타와 후속 연동**에만 영향을 준다.
  "참석자를 넣으면 화자가 분리된다"는 오해를 UI 문구로 유발하지 않아야 한다.

### D5. staging 재업로드 (비효율)

- 근거: 녹음 경로는 성공한 staging 토큰을 캐시하지만(`RecorderView.tsx:348`),
  파일 경로는 캐시 없이 매 시도마다 재업로드한다(`FileUploadView.tsx:152`).
- 영향: STT 실패 후 재시도할 때마다 최대 500MB 를 다시 올린다.
  긴 회의 음원에서 체감이 크고, 서버 staging 디스크에도 고아 파일이 쌓인다.

### D6. mimeType 하드코딩 (잠재 결함)

- 근거: `useAudioRecorder.ts:110` 은 `audio/webm` 미지원 브라우저에서 `audio/mp4` 로
  녹음하지만, `RecorderView.tsx:360` 은 `processMeetingAudio(base64data, 'audio/webm', ...)`
  로 항상 webm 을 보낸다.
- 영향: 현재는 백엔드 `_load_via_ffmpeg`(`/app/src/audio_io.py:46`)가 확장자가 아닌
  내용으로 디코딩하므로 실동작이 깨지지 않는다. 그러나 계약상 거짓이고,
  향후 확장자 기반 분기를 추가하면 즉시 깨진다.

### D7. 로직 표류 (구조적 원인)

- 두 화면에 다음이 각각 복사되어 있다: staging 업로드, 폴링 상태 5종
  (`procStatus`/`procHint`/`procWarning`/`elapsed`/`abortRef`), 취소, 에러 코드 3종 분기,

- D5(캐시가 한쪽에만 있음)와 D6(한쪽만 하드코딩)이 바로 이 복사 구조의 산물이다.
  개별 결함을 고쳐도 구조가 남으면 다음 기능에서 다시 갈라진다.
- S4(훅 추출)가 이 항목을 겨냥한다.

## 4. 설계

### 4.1 목표 구조

화면은 둘 다 남기고, 그 아래 공용 레이어를 만든다.

```
  [사이드바 "새 회의 시작 (녹음)"]      [사이드바 "파일 업로드"]
              |                                  |
        RecorderView (유지)              FileUploadView (유지)
        - 마이크 선택                      - 드래그앤드롭/확장자 검증
        - 녹음 상태 머신 4단계             - 회의 기본정보 폼
          (보정 제거)                      - 결과 미니뷰 + 내보내기
        - ready 핸드오프
              |                                  |
              +----------------+-----------------+
                               |
              +----------------+-----------------+
              |                                  |
     useMeetingAnalysis (신규 훅)      공용 입력 컴포넌트 (신규)
     - staging 업로드 + 토큰 캐시        - ParticipantPicker
     - processMeetingAudio + 폴링        - CalendarEventPicker
     - 진행 상태(status/hint/            - ExportActions
       warning/elapsed)
     - 취소(AbortController)
     - 에러 분기(auth/engine/stalled)
     - beforeunload 경고
                               |
                    draftToMeeting (신규 변환 함수)
                               |
                  handleMeetingProcessed (기존)
                               |
                          ReviewView
```

**화면 통합은 하지 않는다.** `NewMeetingView` 는 도입하지 않고,
`FileUploadView` / `RecorderView` 는 계속 각자의 파일로 존재한다.

### 4.2 신규 모듈 명세

#### `src/hooks/useMeetingAnalysis.ts` (신규) - 이번 작업의 핵심

```
useMeetingAnalysis(opts?: { guardUnload?: boolean }) -> {
  // 상태
  status: 'idle' | 'queued' | 'processing' | 'done' | 'error' | 'cancelled',
  procStatus: string,          // 백엔드 raw status
  procHint: string | null,     // reasonHint (재가공 금지, 그대로 표시)
  procWarning: string | null,  // 'stt_stalled' 등
  elapsed: number,             // 초
  errorMessage: string | null,
  errorCode: string | null,    // claude_auth_expired | stt_engine_error | ...

  // 동작
  analyze(input: { blob: Blob; mimeType: string; filename?: string;
                   participants: Speaker[] }) -> Promise<AnalysisResult>,
  cancel(): void,
  reset(): void,

  // 부가
  stagingToken: string | undefined,   // 캐시됨. 동일 blob 재시도 시 재업로드 없음
}
```

책임:
- staging 업로드를 STT 와 병행 시작하고 성공 토큰을 캐시(D5 해소).
  캐시 키는 blob 참조 동일성. `reset()` 또는 새 입력 시 무효화.
- `beforeunload` 경고를 훅이 소유. 단, 녹음 경로는 `ready` 상태에서도 경고가
  필요하므로(`RecorderView.tsx:312`) `guardUnload` 로 화면이 조건을 확장한다.
- 경과시간 타이머를 훅이 소유.
- 에러 코드 분기 문구를 한 곳에 모아 두 경로 문구가 갈라지지 않게 함.
- `mimeType` 은 호출부가 준 실제 값을 그대로 전달(D6 해소).

훅이 하지 않는 것: 화면 전환, 저장, 상태 머신 관리. 이것들은 각 화면이 유지한다.

#### `src/components/meeting/ParticipantPicker.tsx` (신규)

`RecorderView.tsx:581-708` 에서 추출. 명부 조회(`memberService.getDirectory`),

| `googleEventId` | draft 에 있으면 전달(두 경로 공통) | D1 |
| `audioStagingToken` | 훅이 캐시한 토큰 전달 | D5 |

`duration` 을 백엔드 값 우선으로 정하는 이유: `recordingTime` 은 일시정지 중 타이머를
멈추므로(`useAudioRecorder.ts:150,159`) 실제 오디오 길이와 대체로 일치하지만,
"둘 중 하나"를 매번 고르는 규칙보다 단일 정본이 낫고, 백엔드는 실제 디코딩 길이를 안다.

`handleMeetingProcessed`(`src/App.tsx:368`)의 `baseMeeting` 하드코딩 목록도
`draftToMeeting` 결과를 그대로 받도록 바꿔, **필드를 추가할 때마다 유실되는 구조
(D1 의 근본 원인)** 를 제거한다.

### 4.4 프로젝트명 / host 처리 (2단계)

`Meeting` 타입에 신규 필드를 추가하지 않는다. 기존 `host` 를 그대로 쓰되 두 단계로 나눈다.

**1차 (현행 유지, 신규 작업 없음)**

- 파일 업로드: "프로젝트 명 / 소속" 입력값 -> `Meeting.host`
  (`FileUploadView.tsx:459` 의 현행 동작 그대로)
- 녹음: 로그인 사용자 표시명 -> `Meeting.host`

두 경로가 같은 필드에 다른 의미를 넣는다(파일=프로젝트/소속, 녹음=진행자).
이는 **의도된 절충**이며 스키마 변경을 미루기 위한 선택이다.
2차에서 캘린더가 값을 채우기 시작하면 자연스럽게 "그 회의의 주체"로 의미가 수렴한다.

**2차 (캘린더 연동 이후)**

캘린더 일정을 고르면 이벤트가 가진 정보로 `host` 를 프리필한다.
`google_calendar.list_events`(`/app/src/web/google_calendar.py:36`)는 원시 event dict 를
그대로 내려주므로 `organizer` 필드를 쓸 수 있다.

```
캘린더 일정 선택 시 채워지는 값
  event.summary                                  -> 회의 제목
  event.organizer.displayName || .email          -> host       <- 2차 신규
  event.attendees[]                              -> 참석자(중복 제거 병합)
  event.location                                 -> 장소        <- 파일 화면에만
  event.id                                       -> googleEventId
  event.start.dateTime || event.start.date       -> 날짜(ISO 정규화 필수)
```

- 프리필은 **덮어쓰기 가능**하다. 사용자가 이미 입력한 값이 있으면 확인 없이 덮지 않고,
  비어 있을 때만 채운다(참석자는 기존 정책대로 병합).
- `organizer` 가 없는 일정(개인 생성 등)도 있으므로 부재 시 조용히 건너뛴다.
- 이 동작은 두 화면 모두에 적용된다(`CalendarEventPicker` 의 `onPick` 처리 공용).

### 4.5 결과 확정: 자동 저장 + 버리기

파일 업로드의 "저장하지 않고 전사만" 용도는 **버튼 하나 누락으로 결과가 날아가는
사고를 만들지 않으면서** 보존한다.

```
분석 완료
   |
   +-- 자동 저장(초안, status='review')  <- 녹음 경로와 동일하게 즉시 영속
   |
   +-- 파일 업로드 결과 화면 유지(현행 미니뷰)
         [검토 화면으로 이동]        -> ReviewView (id 확보 상태)
         [JSON 저장] [텍스트 저장] [복사]  -> ExportActions
         [저장하지 않고 버리기]      -> 확인 후 meetingService.deleteMeeting
```

- 자동 저장은 `handleMeetingProcessed` 가 이미 하는 일이므로 신규 로직이 아니다.
- "버리기"는 `meetingService.deleteMeeting`(`src/services/meetingService.ts:96`)과
  `deleteMeetingCore`(`src/App.tsx:170`)가 이미 존재하므로 재사용한다.
- 버리기는 되돌릴 수 없으므로 확인 대화상자를 둔다.
- 녹음 경로에는 이 버튼을 두지 않는다(녹음본은 재취득 불가 - 실수 삭제 위험이 비대칭).

### 4.6 내보내기 배치

- `FileUploadView` 결과 화면: 현행 유지(`ExportActions` 로 교체하되 동작 동일).
- `ReviewView`: `ExportActions` 신규 추가. 현재 ReviewView 에는 JSON/TXT 내보내기가
  없어(확인함) 녹음 경로 사용자는 내보낼 방법이 없다. 이번에 대칭을 맞춘다.

### 4.7 화자 보정(calibration) 단계 제거

현재 보정 단계는 참석자별로 문장을 읽게 하고 `isCalibrated` 플래그만 세운다.
이 값은 **백엔드로 전송되지도, 저장되지도, 사용되지도 않는다**(화자분리 v1 미적용).
사용자에게는 "목소리를 등록하면 화자가 구분된다"는 잘못된 기대를 준다. 제거한다.

**제거 범위 (전부 `RecorderView.tsx` 내부. 다른 소비처 없음 - 확인함)**

| 대상 | 처리 |
| --- | --- |
| `step` 유니언(`:32`) | `'setup' \| 'recording' \| 'ready' \| 'processing'` (4단계) |
| `calibratingIndex` 상태(`:36`) | 삭제 |
| `startCalibration`(`:249`) / `handleCalibrationNext`(`:272`) | 삭제 |
| calibration 렌더 블록(`:758-815`) | 삭제 |
| 진행 바 width 매핑(`:462`) | setup 33% / recording 66% / ready 85% / processing 100% |
| setup 하단 버튼 2개(`:713`, `:728`) | "녹음 시작" 단일 버튼(현 `skipCalibration` 로직 = `startRecording`) |
| `isCalibrated: false` 세팅(`:108`, `:194`, `:209`, `:886`) | 삭제 |
| `Speaker.isCalibrated`(`src/types.ts:11`) | **타입은 optional 로 유지**(기존 저장 회의 호환), 신규 생성 시 미설정 |
| `permissionError` 안내 블록(`:736`) | **유지** - `startRecording` 실패 시에도 필요 |

**주의: 마이크 라벨 회귀**

`enumerateDevices()` 는 마이크 권한 허용 전에는 `label` 을 빈 문자열로 준다.
현재는 `startCalibration` 이 `startMonitoring()` 으로 권한을 얻은 뒤
`refreshAudioDevices()` 를 다시 불러 라벨을 채운다(`RecorderView.tsx:253-257`).
보정을 제거하면 이 경로가 사라져 **마이크 선택 드롭다운이 "마이크 1 / 마이크 2"로만
표시되는 회귀**가 생긴다.

대응: 마이크 드롭다운을 **처음 펼칠 때** 1회 `startMonitoring()` -> `refreshAudioDevices()`
-> `stopMonitoring()` 을 수행해 권한과 라벨을 확보한다. 드롭다운을 열지 않는 사용자는
권한 요청 없이 바로 "녹음 시작"으로 갈 수 있다(현행 `skipCalibration` 과 동일한 경험).

## 5. 파일 업로드의 Google 캘린더 연동

### 5.1 가능 여부: 가능하다 (백엔드 변경 없음)

- `GET /api/google/calendar/events`(`/app/src/web/app.py:2729`)는 `timeMin`/`timeMax`를
  RFC3339 문자열로 그대로 받는다. 미지정 시에만 `now ~ now+CALENDAR_WINDOW_DAYS` 기본값이
  적용된다. **과거 구간 조회에 제약이 없다.**
- 프론트 `integrationService.fetchGoogleCalendarEvents(timeMin, timeMax)`
  (`src/services/integrationService.ts:457`)도 이미 두 인자를 그대로 전달한다.
- 즉 지금 "이번 주"로 보이는 것은 `RecorderView.tsx:86` `thisWeekRange()` 가
  호출부에서 범위를 그렇게 고정했기 때문이며, 백엔드/서비스 계층 제약이 아니다.

### 5.2 조회 범위

파일 업로드의 주 용도는 **이미 끝난 회의의 음원**이다. "이번 주" 고정을 그대로 쓰면
지난달 회의 음원을 올릴 때 후보가 하나도 안 뜬다. 화면별로 범위를 달리한다.

| 화면 | 범위 | 근거 |
| --- | --- | --- |
| `RecorderView` | 이번 주(일 00:00 ~ 다음 주 일 00:00) | 현행 유지. 지금 하는 회의를 고른다 |
| `FileUploadView` | **입력된 회의 날짜 -3일 ~ +3일 (7일 창)** | 날짜를 정확히 기억 못 해도 후보가 잡힌다 |

파일 업로드 화면에는 이미 날짜 입력란이 있으므로(`FileUploadView.tsx:324`)
추가 UI 없이 범위가 결정된다.

```
1) 사용자가 회의 날짜 지정 (기본값 = 오늘)
2) [캘린더에서 일정 불러오기] 클릭
3) 지정 날짜 -3일 ~ +3일 범위의 일정 목록 표시
     - 목록에 각 일정의 날짜를 함께 표시(±3일이라 다른 날 항목이 섞이므로 필수)
     - 0건이면: "해당 기간에 일정이 없습니다" 안내만. 자동 확장은 하지 않는다
4) 일정 선택 -> 4.4 의 프리필 규칙 적용
5) 날짜 입력을 바꾸면 목록을 무효화하고 다시 불러오게 한다
```

**±3일은 잠정 기본값이다.** 실사용에서 부족하다는 피드백이 나오면 그때 넓힌다
(범위 선택 UI 추가 또는 상수 조정). 처음부터 넓게 잡아 목록을 길게 만들지 않는다.

### 5.3 노출 조건과 실패 처리

`RecorderView` 의 현행 규칙을 그대로 따른다(`RecorderView.tsx:77-83, 113-120`).

- 마운트 시 `integrationService.getGoogleStatusSafe()` 1회 확인.
  미연동이면 캘린더 버튼 자체를 숨긴다(빈 기능 노출 금지).
- `google_auth_expired` -> "인증 만료 - 설정에서 다시 연결해주세요" + 버튼 숨김
- `google_not_connected` / 401 -> "Google 미연동 - 설정에서 연결해주세요" + 버튼 숨김
- 그 외 오류 -> 백엔드 detail 문구 표시. **캘린더 실패가 파일 분석을 막지 않는다.**

### 5.4 주의: 종일 일정

Google 이벤트는 `start.dateTime`(시각 있음) 또는 `start.date`(종일)를 준다.
현행 매핑(`RecorderView.tsx:102`)은 둘 다 받아 폴백하지만, 종일 일정은
`'YYYY-MM-DD'` 문자열이라 그대로 `Meeting.date` 에 넣으면 **D2(포맷 불일치)를
새 경로에서 재생산**한다. `draftToMeeting` 의 ISO 정규화를 반드시 통과시켜야 한다.

### 8.3 회귀 체크리스트

- 대시보드/기록 목록의 날짜 라벨이 "날짜 없음" 으로 바뀌지 않을 것
- 뒤로가기(`tabHistory`) 동작 유지
- 파일 업로드에서 참석자/캘린더를 **비워둔 채** 분석 시작이 여전히 가능할 것
- 기존 저장 회의의 참석자에 `isCalibrated` 가 남아 있어도 조회/편집 정상
- 관리자/비관리자 진입점 노출 변화 없음
- 기존 저장 회의(구 포맷 `date`) 조회 정상

## 9. 리스크와 완화

| 리스크 | 완화 |
| --- | --- |
| 보정 제거로 마이크 라벨이 빈 값이 됨 | 4.7 의 드롭다운 지연 권한 요청. V2/V3 로 검증 |
| 보정 제거를 기능 축소로 받아들임 | 릴리스 노트에 "해당 기능은 화자분리 미적용으로 실제 효과가 없었음"을 명시 |
| 훅 추출 중 폴링/취소 로직의 미묘한 변경 | S4 는 화면 UI 를 건드리지 않고 로직만 이동. V9~V12 로 검증 |
| 파일 업로드 화면이 무거워져 "경량 도구" 성격 상실 | 참석자/캘린더를 접힌(collapsed) 선택 영역으로 배치. 기본 흐름(파일 -> 분석)은 클릭 수 불변 |
| `date` 포맷 변경이 기존 데이터와 충돌 | 저장 포맷만 통일하고 읽기는 기존 폴백 유지. 마이그레이션 불필요 |
| ±3일 범위가 실사용에 부족 | 잠정값임을 명시(5.2). 상수 1개 조정으로 확장 가능하게 구현 |
| host 필드의 이중 의미(프로젝트 vs 진행자) | 1차는 현행 유지, 2차 캘린더 프리필로 수렴. 스키마 변경 없음(4.4) |
| "버리기" 오조작 | 확인 대화상자 필수. 녹음 경로에는 미도입 |
| `.flac` 등 확장자 처리 회귀 | 7절 "손대면 안 되는 것" 준수 + V25 |
